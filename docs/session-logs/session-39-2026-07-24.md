## Key decisions

Kickoff research (before plan-mode design work, not a live-conversation
design pass — this session isn't a doc-only session, so `.claude/
dev-session.md`'s live-decisions override doesn't apply here) found three
real gaps beyond what the design doc anticipated:

- **`fontSources.js` had no way to change the calibration reference after
  the first source registers.** The editor spec assumes an author can
  reassign it ("a real, semi-destructive action... deserving a clear
  confirmation step"), but `referenceRatio` locks in permanently once
  non-null, with no mutator. Confirmed with the user via `AskUserQuestion`
  before planning: add `setReferenceFontSource(fontSourceRegistry, id)`,
  recalculating every other registered source's calibration via the
  existing `deriveCalibration`.
- **`registerFontSource` always internally re-derives calibration** — it
  has no parameter for a caller-supplied one. A slider drag can't route
  through it without silently discarding the dragged value every time; the
  only way a manual override persists is mutating the raw registry
  directly via `register(fontSources.registry, id, {...}, { override: id })`,
  bypassing `registerFontSource` entirely for that one call site.
- **`fontSourceRegistry` had no field recording which source is currently
  the reference.** A derived-numbers-based guess (checking for identity
  scale/offset) would false-positive whenever two sources happen to share a
  vertical-span ratio. Added a `referenceId` field, set by both the
  implicit-first-registration branch and `setReferenceFontSource`.

The `NarrowForm.svelte`/`narrowForm.js` shared form primitive was
deliberately **not** reused for the calibration sliders — `editor.md`
itself already decided this in its "Narrow shared form primitive" section:
`horizontalCenteringMode` is a fixed enum a `typeof`-based inference can't
produce, so calibration tuning (like keybinding/palette/config UI) stays
individually-built.

## Notes

Browser verification caught a real reactivity bug before checkpoint 2's
commit: the list-panel's reference badge called `isReferenceFontSource`
directly inside the `{#each}` template block, with no `refreshToken` read
to gate it — since `fontSources` mutates an internal `Map` in place
(`registry.js`), Svelte 5's fine-grained reactivity had no way to know the
badge needed to re-render after `setReferenceFontSource` ran, even though
every other derived value in the same component (which does read
`refreshToken` first, mirroring `ContentBrowser.svelte`'s
`liveRefreshToken` pattern) updated correctly. Fixed with a dedicated
`currentReferenceId` derived value read the same gated way. Consistent with
this project's established pattern: `.svelte` logic isn't unit-tested, only
extracted `.js` modules are, so this class of bug only ever surfaces during
live manual verification.
