## Fixes

1. **`save.js`'s `deserialize` never forwarded `isWalkable`/`isOpaque` to
   `createApi`** (`917100f`). `serialize`/`deserialize` round-trip
   `seed`/`platform` through, but not the map-query closures — any
   restored `api` (glyphkeep's `dev.html` HMR snapshot restore; later,
   any real save/load) lost `findPath`/`computeFov` entirely. Fixed by
   adding `isWalkable`/`isOpaque` to `deserialize`'s options, threaded to
   `createApi`. Regression test in `save.test.js`.
2. **`computeFov`/`fovContains` (`fov.js`) were never exported from
   `index.js`** (`11c3b9d`). Implemented and tested internally
   (`fov.test.js`), reachable only via `api.computeFov`'s player-FOV-
   bound wrapper — contradicts `docs/design/rendering.md`'s "one shared
   shadowcasting primitive, three consumers" framing (player FOV,
   per-monster perception, light-source propagation), which needs a raw
   `computeFov` callable with a caller-chosen `isOpaque`. Two-line export
   addition; new `index.test.js` regression test guarding the public
   surface generally (no prior convention tested the export list itself).
3. **`act()`/`run()` (`engine.js`) hung forever instead of erroring when
   called against an empty scheduler** (`9a1efbe`). `next(scheduler)`
   correctly returns `undefined` for "no actors registered," but `act()`
   fell straight through to `dispatchExclusive`/`spend` with
   `entity=undefined` anyway — `spend` has no existing-actor guard, so
   this corrupts `scheduler.actors` with a `NaN`-budget entry, which then
   makes every future `next()` call return `undefined` too, forever, with
   no lock ever set to stop `run()`'s `while (!engine.locked)` loop.
   glyphkeep hit this in its checkpoint 2 (calling `run()` before adding
   its player as a scheduler actor) but worked around it in the moment
   without logging it as a real engine gap — only caught at glyphkeep's
   own close-out, via its Tokenote companion notes flagging it in real
   time during the session. Fixed with an early-return guard in `act()`
   (`entity === undefined` → `{ entity: undefined, waiting: false, idle:
   true }`) and a loop-break in `run()` on that `idle` flag. Two new
   regression tests in `engine.test.js`.
4. **`create-glyphrogue-game`'s scaffold template shipped with no
   `.gitignore`** (`9a1efbe`, same commit as above — same Tokenote
   source, same close-out). Every generated game's `node_modules`/`dist`
   were one `git add .` away from being committed. Fixed by adding
   `packages/cli/templates/default/.gitignore`; new regression test in
   `packages/cli/test/scaffold.test.js` runs `copyTemplate` against the
   *real* template directory (not a synthetic fixture) and asserts the
   file copies through.

Test count: 567 → 572 (`core` 358→361, `cli` 5→6). No `packages/editor`/
`packages/input` changes.

## Follow-up: a real scaffold template bug, found deploying glyphkeep for real

One more fix landed after this session's initial close-out, while
glyphkeep added a GitHub Pages link to its own README and discovered
both its `deploy-pages` runs had actually been failing. Two of the three
causes were glyphkeep-side CI configuration (see glyphkeep's own session
2 log's "Follow-up" section) — but the third was a real bug in this
repo's own scaffold template: `packages/cli/templates/default/
vite.config.js` hardcoded the Pages-mode `base` as root `'/'`, correct
only for a `<user>.github.io` root repo or a custom domain, not this
scaffold's own normal case (an ordinary project repo, served from
`/<repo-name>/` — every generated game deployed to Pages the normal way
would 404 on every built asset). Fixed by templating the game name into
the base path (`5591479`), with a regression test in `packages/cli/test/
scaffold.test.js` asserting the real template substitutes it correctly.
Verified against glyphkeep's own real production deploy after the fix,
not just the test suite — real keyboard input moved the player on the
live site, zero console errors.
