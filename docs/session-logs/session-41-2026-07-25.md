## Key decisions

- **The pre-publish problem.** `@glyphrogue/core`/`@glyphrogue/editor`
  have never been published to npm, but `build-pipeline.md`'s scaffold
  design assumes published packages. Resolved: the scaffold writes real
  semver ranges (`^0.1.0`) against the eventual published names, never a
  `file:`/`link:` workspace reference (which would silently break for
  every real user, since a scaffolded game is its own separate repo, not
  a monorepo workspace member). Publish early under `0.x` rather than
  waiting for "polished" — `0.x` is npm/semver's built-in "no stability
  promises yet" signal, and "polished" has no real finish line while the
  roadmap keeps growing. The actual first `npm publish` is a manual
  prerequisite step that belongs at `packages/cli` *implementation* time,
  not this design session.
- **CLI invocation shape.** Prompts for the game name only (target
  directory defaults to a kebab-cased version, `create-vite`-style). No
  non-interactive/flag-driven mode — nothing in the roadmap needs scripted
  scaffolding yet, and it's small additive surface to add later if that
  changes.
- **Starter example bar.** Each starter content-folder example
  demonstrates the simplest correct path through its own package's
  system, not an advanced feature: a hand-placed static room (not a
  generator call — that's the map editor's job), one plugin registering a
  single trivial entity type, one already-calibrated font source. Bar:
  runs with zero required edits, nothing requires reading a design doc to
  modify. User flagged richer example projects as worth a long-term
  backlog item, not this session's job.
- **Substitution mechanism.** Plain fixed-token string replacement
  (`__GAME_NAME__`-style), no templating engine — matches
  `build-pipeline.md`'s existing "no templating framework" decision; two
  known substitution sites don't justify a dependency.
