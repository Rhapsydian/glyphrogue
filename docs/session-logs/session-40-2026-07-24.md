## Key decisions

Kickoff research found two real gaps behind the spec, both resolved with
the user via `AskUserQuestion` before planning:

- **No raw-capture primitive exists.** `keyboardSource.js` and
  `gamepadSource.js` both gate everything through `resolveBinding` — they
  only ever report an input already mapped to an action. The Keybindings
  tab's "listen for your next keypress" affordance needs the opposite:
  report whatever raw key/button/axis fires next, regardless of binding
  state. Resolved by adding `packages/input/src/captureBinding.js` as a
  new, game-agnostic primitive (not editor-only — a real game's own future
  remap screen would need the same thing), rather than duplicating raw
  listener logic inside the editor package.
- **No audio asset exists to preview with**, and `audio.js`'s
  `playSound`/`playMusic` both require an already-decoded `AudioBuffer`.
  Resolved: synthesize a short in-browser test tone (a real `AudioBuffer`,
  no external asset) so the Audio tab's sliders drive genuinely audible
  playback through the real `playMusic`/`playSound` functions, rather than
  shipping sliders with no live-preview fidelity.

A third gap — no "default-settings source" file/format convention exists
anywhere in the codebase for what the spec calls "the game's own
default-settings source" — was resolved by following the Map Editor /
Composition Tool precedent exactly: each tab has its own author-specified
destination-path text field (sensible default), not a new hardcoded
convention.

## Notes

After checkpoint 3 was committed and reported done, the user reported the
synthesized test tone was still audibly playing. Root cause:
`previewMusic` called `playMusic(audioCtx, buffer, { volume })` without an
explicit `loop`, so it inherited `playMusic`'s own `loop: true` default —
and no Stop control existed anywhere in the UI, so the tone looped
indefinitely once triggered. Fixed immediately in two steps: (1) killed
the already-playing audio by reloading the stale browser tab (a full
navigation tears down a page's `AudioContext`s, which a stopped dev server
alone does not — the already-loaded page keeps running its own JS
regardless of server state), then (2) fixed `previewMusic` to pass
`loop: false` explicitly, matching `previewSfx`'s already-correct
non-looping behavior — a synthetic test tone has nothing worth
looping-auditioning, so a brief one-shot is the right fix rather than
adding a Stop button for a sound that should never run long enough to
need one. Verified the fix directly against the real Web Audio API
(dynamically importing `configAudio.js` in-page and confirming the
returned source's `onended` fires on its own). Committed separately
(`463e118`) rather than folded into checkpoint 3, since it was found and
fixed after that checkpoint's commit and sign-off. Lesson for future
sessions: when reusing a `core` playback function with its own
opinionated defaults (`loop: true`), always pass every parameter a preview
caller needs explicitly rather than relying on a default that's correct
for one caller (a real looping music track) but wrong for another (a
one-shot sanity check with no stop control).
