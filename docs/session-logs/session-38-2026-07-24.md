## Key decisions

A long plan-mode conversation (not a forced-choice ritual — broad-strokes
discussion, per this project's own established preference) worked through
what the wizard actually needed to do, in order:

- **What's being composed.** Not map generation (that's item 6, already
  done) — connecting entity types to rules. Both `registerEntityType` and
  `registerRule` ultimately reduce to the same `components` filter
  mechanism; the distinction is just filter *shape*: a plain marker
  component (global/reusable, e.g. `Wanders`'s `{ all: ['Wanders'] }`) vs.
  a filter naming the synthetic `EntityType` component (type-pinned, e.g.
  `{ component: 'EntityType', equals: { type: 'guard' } }` —
  `registerEntityType`'s inline `rules` sugar auto-generates this shape,
  but nothing stops a standalone `registerRule` call from using it too).
- **The doc's "never writes a file" premise doesn't survive contact with
  `registry.js`'s actual `override` mechanism.** `register()` already
  supports whole-value replace via `options.override: id`. `api.js`
  already had `getEntityDefinition(id)` but was missing a `getRule(id)`
  equivalent. Once added, both wizard operations become plugin code that
  runs *after* its target is already registered (via normal
  `dependencies` ordering), reading the live value back and
  re-registering with one field changed — never needing to know where the
  original definition lives. This flips the wizard from
  copy-paste-instructions-only to a real file-writer, correcting the
  design doc.
- **Two outputs with genuinely different lifecycles**, surfaced when the
  user asked about editing/deleting generated compositions later:
  attach/widen entries are pure data (safe to regenerate blindly, so a
  generated composition plugin exports both the entries array and a
  data-driven `register()`), while a genuinely new rule's handler body is
  hand-written the moment the author touches it — so custom scaffolds stay
  one-shot writes the wizard never revisits, matching the doc's original
  "in their own editor" framing (just scoped correctly, to only that
  case).
- **Full CRUD, multiple compositions, and a real delete** were the user's
  explicit asks, worked out together: delete only when a composition is
  empty, disabled, and nothing else depends on it — the first
  delete-capable endpoint this project has built (every prior write tool
  stayed additive-only).
- **`applyRuleOverride` belongs in `packages/core`, not
  `packages/editor`** — caught mid-implementation, not in planning.
  Generated composition plugin files ship as part of a downstream game's
  own source and import this at real runtime; `packages/editor` is
  dev-time-only tooling that never ships. The plan's own file list had
  this wrong; moved during checkpoint 2 with no other design impact.
- **`dependencies` on a generated composition plugin stays core-only, not
  auto-derived** from its entries' targets — a target (an entity type, a
  rule) isn't guaranteed to come from a plugin at all, e.g. a game's
  bootstrap file registering an entity type directly outside `loadPlugins`
  entirely. No reliable id exists to point at; the author adds one by hand
  if genuinely needed.

## Notes

Three real bugs surfaced only during live browser verification, none
caught by unit tests (consistent with this project's established
"`.svelte` logic isn't unit-tested, only extracted `.js` modules are"
posture):

- **`registeredId` gap** — `pluginCatalog.js` catalog entries only carried
  a plugin's own id, which isn't guaranteed to equal the actual id passed
  to `registerRule` for a custom (non-first-party) plugin. Widen entries
  need the real registered id; fixed by threading `registeredId` from the
  manifest's first entry through.
- **Stale browser module cache** — `discoverCompositions`'s dynamic
  `import()` had no cache-busting. A composition plugin is the first kind
  of candidate a session can realistically rewrite more than once
  (save → edit → save again), and the browser's native ES module cache
  serves the first-loaded module for a URL forever regardless of Vite's
  own file-watching, since a fully dynamic runtime `import()` isn't one of
  Vite's statically-tracked/HMR-invalidated imports. Fixed with a `?t=`
  query param, mirroring the cache-busting the `/delete` endpoint's
  Node-side dynamic imports already needed for the same reason.
- **Delete was unreachable through the UI** — `canSaveComposition`
  required at least one entry, but `canDeleteComposition` requires the
  *saved* file to already have zero entries. A real catch-22, only caught
  by actually trying to walk the full delete path live rather than
  reasoning about it from the code.
